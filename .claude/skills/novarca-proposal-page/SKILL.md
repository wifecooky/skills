# Novarca 社内提案ページ

これからやることを提案し、承認と協力をもらうための日本語の 1 ページ。
読み手は時間のない非エンジニアの管理者。見た目と部品は `template.html`、完成例は `examples/bdx-assistant.html`（BDX Bot に判断事例の検索を付ける提案）。
完成例は公開した時点の版で、その後に直した点（`span.nw`、figs の dt→dd の順、週数の自動目盛り）は入っていない。節の順番と冒頭の数字は v7 で直してあり、完成例どおり。完成例と template が違うときは template に従う。

## novarca-tech-report との使い分け

| | novarca-proposal-page | novarca-tech-report |
|---|---|---|
| 書くこと | これからやること | 終わった検証の結果 |
| 読み手にしてほしいこと | 承認・協力 | 結果を知る |
| 最後の節 | お願い（担当付き） | うまくいかなかった方法・運用ルール |

検証の結果を報告しつつ次の承認も欲しいときは、報告を tech-report で作り、提案ページの「参考」からリンクする。1 ページに混ぜない。

## 手順

1. **素材を集める。** 素材ファイル（例：material.md）にないことは書かない。足りなければユーザーに聞く。
   - 宛先・作成者・作成日
   - 何をするか 1〜2 文と、その狙い
   - 提案のもとになった分析があれば、その数字（期間・対象・件数・出所）
   - 課題、Bot と人の分担、最初に作るもの
   - フェーズ（週数・内容・次へ進む判定）、体制と費用
   - リスクと対策、お願い（担当付き）
2. **`template.html` をスクラッチパッドにコピー**して中身を差し替える。`〔…〕` はすべて素材の言葉に置き換える。使わない節は丸ごと消し、ナビの項目も消す。CSS のトークンと部品はそのまま使い、新しい色を足さない。
3. **スクリーンショットを 1 回撮る**（下の「確認」）。見つけた問題はまとめて直す。撮り直しは最大 1 回。
4. **公開**は Artifact ツール（初回 `icon: "document"`）。修正は同じファイルパスで再公開し、URL を保つ。
5. **返信**は、変えた点の箇条書きとリンクだけ。公開先は非公開で、共有はページの Share から行う、と一言添える。

## 節の順番（固定）

提案書の流れは「課題 → 提案 → お願い」。お願いは最後の本文の節。
冒頭の数字は提案の要点（どこで・どれだけ試すか、何を頼むか）にする。調査や分析の数字を冒頭に置かない。
提案のヒントを探した調査・分析は、お願いの後に「参考」として置く。冒頭や課題の前に置くと、正式な現状調査に見える。

| # | 節 | 部品 | 中身 |
|---|---|---|---|
| 1 | ヘッダー | `h1`、`.what`、`.meta`、`dl.figs` | タイトル、何をするか、宛先・作成・日付、提案の要点 3 つ |
| 2 | 課題 | `ul.issues` | カード 4〜6 枚。根本原因は左の `.take`。実害の数字はカードの `em` |
| 4 | 分担 | `.lanes` ＋ `p.guard` | 左に Bot、右に人。動詞で分ける。Bot の制約 |
| 5 | 最初に作るもの | `ol.flow`、`dl.fields`、`ul.rules`、`table.cmp` | 流れ 3〜5 手、台帳の項目、データの決まり、既存との比較（あれば） |
| 6 | 実施計画 | `ol.steps`（script の `phases`）＋ `dl.cost` | フェーズごとに週数・内容・次へ進む判定。体制と費用 |
| 7 | リスクと対策 | `ul.risks`（script の `risks`） | [リスク, 対策] |
| 8 | お願い | `ol.asks` | 1 件目は承認。各件に担当（`.who`） |
| 9 | 参考（あれば） | `.legend` ＋ `ul.bars`（script の `tasks`） | 提案のもとになった分析。見出しは「参考：〇〇の分析」。補足に何のために見たかを書く |
| 10 | フッター | `.foot` | タイトル ・ 作成者 ・ 日付 |

- **各節の左側（`.rail`）は、見出し・結論 1 文・補足 1 文。** 結論の 1 文は、忙しい人が左だけ読んでも分かるように書く。素材の言葉を要約してよいが、新しい事実は入れない。
- **冒頭の数字は提案の要点 3 つ。** この順に選ぶ：
  1. 試す範囲と期間（例：約 1 か月、1 グループ）
  2. 既存のもので足りる根拠（例：Bot の参加先の数）
  3. 相手に頼む負担（例：週約 1 時間）
  - ラベル（`dt b`）は 6 文字以内。スマホでは補足の `span` が消え、ラベルだけが 3 列に並ぶ。
  - 分析の数字（件数・種類数）は「参考」に、実害の数字は課題カードに置く。
- **参考の色分け（`role`）は、素材の「Bot の役割」の書き方で決める。**
  - `bot`：Bot の役割だけで書かれている。例：「Bot が回答・集約」「Bot が自動検証」「通知のみ Bot」
  - `prep`：Bot の後に人の判断・確認・コメントが続く。例：「条件チェックは Bot、例外判断は人」「集計は Bot、コメントは人」「Bot が申請文を作る」（送るのは人）
  - `human`：Bot の役割がない。
  - 凡例の `（n）` は、その色の業務の種類数。
- **課題カードは 4〜6 枚。** 多いときは、同じ原因のものを 1 枚にまとめる。元の数字は残す。
- **流れは 3〜5 手。** 列の数は手の数に合わせて自動で変わる。
- **計画の週数バーは、最も長いフェーズの週数に合わせて自動で目盛りが変わる。** 実色＝最短、薄い青＝延びた場合。
- **既存の取り組みとの比較**は、定義 1 文 → 比較表 → まとめ方 1 文 → 取り入れること（`ul.rules`）の順。比較がなければブロックごと消す。

## 文言のルール

- **素材にない数字・事実・形容を足さない。** 「毎回」「大幅に」「必ず」のような強める言葉も、素材になければ書かない。
- **概数は「約」を付ける。** 件数が概数であることを出所の注記にも書く。
- **データの出所を書く。** 期間、対象、まだ見ていない範囲。
- **数字と単位は半角スペースで分ける。** 改行は `body` の `word-break: auto-phrase` が文節で入れる。それでも語の途中や数字と単位の間で切れたら、その語を `<span class="nw">` で包む（例：`<span class="nw">1 グループ</span>`）。`&nbsp;` や行内 style は使わない。
- **`.what` は 1〜2 文。** 何をするかと狙いだけを書く。試行の範囲・期間と既存の基盤は冒頭の数字へ、費用は `dl.cost` へ、承認の補足はお願い 1 件目の `span` へ移す。
- **1 行に事実 1 つ。** 3 行を超える段落を作らない。
- **お願いは「何を」＋「量・用途」＋「誰に」。** 補足は `.t span` に 1 行。「誰に」が素材にないときはユーザーに聞く。聞けないときは `.who` を消す。推測で埋めない。
- **個人情報は伏せる。** 社内の担当者名は書いてよい。ID・電話番号・社外の人の評価は書かない。
- **日本語に統一する。** 製品名・ファイル名などの固有名詞だけ例外。

## 見た目のルール

- **モダンな業務文書の見た目。** 浅いグレーの地に白いカード、アクセントは青 1 色、書体は IBM Plex Sans JP。
- **使わない：** A3 用紙風、ハンコ、方眼、紺の帯、丸数字。ユーザーに「正式すぎる・古典的」と却下された。
- **マーケティングのランディングページにしない。** 大きなヒーロー画像、グラデーション文字、太い左罫線、絵文字アイコンを使わない。
- **動きはバーが伸びる 1 つだけ。**

## 確認

Playwright はスクラッチパッドにローカルで入れる（`npm i playwright`）。ブラウザはダウンロードしない。入れた Playwright が求めるブラウザがあればそれを使い、なければキャッシュ済みの headless shell を `executablePath` に渡す：

```js
import { chromium } from 'playwright';
import { existsSync } from 'fs';
const want = chromium.executablePath();
const exe = existsSync(want) ? want : process.env.EXE; // EXE=$(ls -d ~/Library/Caches/ms-playwright/chromium_headless_shell-*/*/chrome-headless-shell | tail -1)
const b = await chromium.launch({ executablePath: exe });
const p = await b.newPage({ viewport: { width: 390, height: 844 }, deviceScaleFactor: 2, reducedMotion: 'reduce' }); // reduce = バーを伸び切った状態で撮る
```

Artifact はページを自動で HTML の骨組みで包む。確認用には、自分で骨組みを付けたファイルを作る：

```sh
{ printf '<!doctype html><html lang="ja"><head><meta charset="utf-8"><meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover"></head><body>\n'; cat index.html; printf '\n</body></html>\n'; } > preview.html
```

撮るもの：1440 幅の全体と最初の画面、390 幅（@2x）の全体と最初の画面、1440 幅のダークモード。390 幅で `document.documentElement.scrollWidth` が 390 であることを出力する。

## 公開前チェック

- [ ] `grep -c '〔' index.html` が 0
- [ ] 素材にない数字・事実・強める言葉がない
- [ ] 最初の画面（PC・スマホとも）にタイトル、何をするか、提案の要点 3 つが見える
- [ ] お願いが本文の最後の節にあり（後ろは「参考」だけ）、各件に担当がある
- [ ] 冒頭の数字に調査・分析の数字を使っていない
- [ ] 各節の左に結論 1 文がある
- [ ] スマホで横スクロールがない（scrollWidth = 390）
- [ ] スマホで数字と単位が改行で分かれていない。見出しが語の途中で切れていない
- [ ] 計画が 1 フェーズ 1 行で、どれにも「次へ進む判定」がある（未定なら「未定」）
- [ ] 概数に「約」、出所の注記がある
- [ ] ダークモードで文字が読める
