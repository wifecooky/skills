# Novarca 社内技術検証レポート

技術検証の結果を、社内の非エンジニアも読める日本語の 1 ページにまとめる。
見た目と部品は `template.html`、完成例は `examples/taobao-patrol.html`（淘宝巡回システムの検証）。

## 手順

1. **材料を集める**
   - 検証条件：環境、アカウント、バージョン、データの出所
   - 結果の数字：件数、成功・失敗、時間
   - 生データ：CSV や表
   - 構成：何が何をどう動かすか
   - 時間の内訳
   - うまくいかなかった方法
   - 運用ルール
   - 足りないものはユーザーに聞く。推測で埋めない。
2. **`template.html` をスクラッチパッドにコピー**して中身を差し替える。使わない節は丸ごと消す。CSS のトークンと部品はそのまま使い、新しい色を足さない。
3. **公開**は Artifact ツール（初回 `icon: "report"`）。修正は同じファイルパスで再公開し、URL を保つ。
4. **返信**は、変えた点の箇条書きとリンクだけ。公開先は非公開で、共有はページの Share から行う、と一言添える。

## 節の順番（固定）

読み手が最初に知りたいのは「何を、どんな条件で試して、どうだったか」。仕組みの説明は後ろに置く。

| # | 節 | 部品 | 既定 |
|---|---|---|---|
| 1 | ヘッダー＋結論 | `.eyebrow`（日付・検証・対象件数）、`h1`、`.lead`、`.chips`、`ul.verdict` | — |
| 2 | 検証条件と所感 | `dl.memo` | 常に開く |
| 3 | 今回の結果 | `.stats` | 常に開く |
| 4 | データ一覧 | `details.fold` ＋ `table.data` | **閉じる** |
| 5 | 構成図 | `details.fold` ＋ タブ（シンプル／詳細） | 開く |
| 6 | 処理の内訳 | `details.fold` ＋ `.bar` ＋ `ol.steps` | 開く |
| 7 | 未検証・次に確かめること | `ul.rules`（`<strong>観点：</strong>` で始める） | 常に開く |
| 8 | うまくいかなかった方法 ／ 運用ルール | `.cols` | 常に開く |
| 9 | フッター | `Novarca 社内技術検証 ・ 作成者 ・ 日付` | — |

- **結論（`ul.verdict`）はヘッダーの中に 3〜4 行。** 忙しい人はここだけ読む。
  - 各行は「ラベル（使える／問題なし／速さ など）＋数字入りの 1 文」。
  - 最後の行は `li.open` で一番大きな「未検証」を書く。良いことだけ並べない。
  - 計算値（例：1 時間あたりの件数）は `<small>` で計算値と注記する。
- **長い節は必ず `details.fold`** で折りたためるようにする。`summary` の `.hint` には件数やステップ数を入れる。
- **構成図の下に「AI の使いどころ」を必ず置く**（`.ai`。タブの外に置き、どちらのタブでも見えるようにする）。
  - 動かす・読む・まとめる の段階ごとに、AI を使ったかを書く。
  - 開発で AI を使ったことは当たり前なので書かない。
  - 使った段階には `class="on"` を付け、タグに「AI あり」と書く。使わない段階のタグは「LLM なし」「端末内」など。
  - 実行時に LLM が要らないなら、はっきり「LLM なしで動く」と書く。OCR などの機械学習モデルは、データを外部に送るかどうかも書く。
  - **構成図の中にも同じタグを付ける。** シンプル版はノードに `span.ai-mark`（使った段階は `.ai-mark.on`）、詳細版は該当ボックスに SVG の `g.tg`（`.tg.on`）。凡例に「AI の使いどころ（下の説明と対応）」を足す。
  - シンプル版の `.flow-notes` の最後に、AI をどこで使うかを 1 行（`.dot.ai`）。
- **構成図は 2 枚とも作る。**
  - シンプル版：アイコン付きのノード 4〜6 個と矢印、その下に色付きの点で 1 文ずつ説明（`.flow-notes`）。
  - 詳細版：SVG 配線図と凡例。
  - 既定のタブはシンプル。

## 文言のルール

ここが一番大事。読みやすさは文の書き方で決まる。

- **タイトルに「検証」を入れる。** 例：「〇〇の検証」「〇〇は△△できるかの検証」。
- **`.lead` は 1 文だけ。** 何を確かめたかだけを書く。技術条件は `.chips` に 3〜5 個のタグとして並べる。
- **長い段落を書かない。** 説明文は箇条書き（`ul.notes`、`.memo dd ul`）にし、1 行に事実を 1 つだけ書く。です・ます調の文末（「〜しました」「〜と考えています」）は落とし、体言止めや短い常体にする。
- **1〜2 文字だけ次の行に落ちる改行を残さない。** 長い行は `<br>→` で 2 行に分けるか、言葉を削る。`.memo strong` は途中で改行しない（`nowrap`）ので、15 文字前後までにする。
- **大事な一言は `<strong>`** で示す。`.memo` の中では蛍光ペン風の下線になる。1 項目につき 1 箇所まで。
- **事実と所感を分ける。** 意見・見立ての行には `class="opinion"` と `<span class="badge">所感</span>` を付ける。
- **データの出所を書く。** 元ファイル名・表名を「」付きで示し、重複除去などの件数の増減も書く。
- **わからないことは「未検証」と書く。** 推定値は「約」を付け、実測か推定かを注記で分ける。
- **手で直した値は注記する。** 例：「No.3 のみ目視で補正」。
- **独自に作った・改修した場合は、試行錯誤の経緯を一言入れる。** どの壁に当たったかを括弧で 2〜3 個挙げる。
- **日本語に統一する。**
  - 中国語や英語の画面文言を混ぜず、日本語の言い方に置き換える。例：滑块 → スライダー認証、登录 → ログイン画面、优惠前 → 割引前。
  - 例外はファイル名・表名・製品名などの固有名詞だけ。
- **社内の業界用語は読み手の言葉にする。** 例：風控 → ブロック検知。
- **数字には単位を付ける**（「34 件」「16.1 秒」）。数字と単位の間は半角スペース。表の数字は `tabular-nums` で揃える。
- **個人情報は伏せる。** 誰の端末・アカウントかは書いてよいが、ID や電話番号などは載せない。

## 部品の使い分け

| 用途 | 部品 |
|---|---|
| ラベル付きの条件・前提 | `dl.memo`（`dt` は 6 文字前後） |
| 結果の数字 4〜6 個 | `.stats`。成功は `.ok`、失敗・停止は `.warn` |
| 大きい生データ | `.dtbl` ＋ `table.data`。行の状態は `.st.ok` / `.st.ng`、対象外の行は `tr.off` |
| 手順と時間 | `.bar`（`flex` 値＝秒数）＋ `ol.steps`。色は `.c1`〜`.c4`、チェック工程は `.cw` |
| 比較表 | `.tbl` ＋ `table`。NG は `td.no`、OK は `td.yes` |
| 補足 | `ul.notes`（`p.note` の長文にしない） |
| 守ること | `ul.rules` |

- 色は `--accent`（主な流れ）、`--ok`（成功・2 本目の流れ）、`--warn`（失敗・停止）の 3 つだけ。
- アイコンは 24×24 の線画 SVG を `stroke="currentColor"` で描く。表、PC、スマホ、OCR 枠、ファイル、盾などの例が template と example にある。
